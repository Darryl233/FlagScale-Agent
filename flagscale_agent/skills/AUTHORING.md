# SKILL 编写框架

SKILL 是 Agent 执行任务的操作指南。正文让执行者知道现在做什么、得到什么结果、接下来走哪一步。
先完成一条可验证的流程，再增加方法；不按知识分类拆出多个重复管理同一任务的 SKILL。

## 统一骨架

| 部分 | 必须回答的问题 |
| --- | --- |
| 输入与完成条件 | 从什么材料开始？这次做到哪里算完成？哪些信息缺失会阻塞执行？ |
| 执行流程 | 按什么顺序操作？每步产生什么？成功、失败或信息不足时走哪里？ |
| 按需扩展 | 在哪一步接入其他方法或工具？需要给它什么，取回什么？ |
| 交付 | 最终交付什么文件和结论？如何区分已验证和未验证？ |

frontmatter 的 `description` 写触发场景；正文沿上述骨架编写。步骤可少可多，以能完成一个具体任务为准。
每步使用“动作 → 产物 → 下一步”，避免只写“分析、优化、验证”而没有可执行动作或判断依据。

## 内容放在哪里

| 内容 | 位置 |
| --- | --- |
| 执行顺序、结果分支、停止与交付 | `SKILL.md` |
| 可替换的候选生成方法及额外检查 | 主技能的 `methods/`，仅在选择该方法时读取 |
| 参数原理、约束、版本兼容性、历史案例 | Knowledge，通过索引按需查询 |
| 需要可靠重复执行的操作 | `scripts/` 和 `assets/`，SKILL 只保留调用入口 |

独立 SKILL 应有可单独提出的用户任务和明确产物。例如 profile 采集可以独立完成；
同一调优任务中的“改批量”和“改重计算”通常只是两种方法，不各自再建运行、排名、复测流程。

## 调优方法的接入约定

主流程管理实验运行、预算、记录、比较和最终采纳。方法文档只包含四项：

1. **适用条件**：需要的配置、运行结果或瓶颈证据；不满足时返回缺口。
2. **生成候选**：从哪个父配置出发、改什么、如何生成一个或少量候选。
3. **额外检查**：该变更特有的合法性、后端生效和正确性检查。
4. **结果反馈**：通过、失败、无收益时如何选择下一个候选或结束该方法。

方法返回 `parent`、`hypothesis`、`change`、`checks`：父配置、待验证假设、可复现配置差异/补丁、额外检查。
这些字段可以写入现有实验记录，不要求新的注册器、Python 接口或单独的候选卡文件。
新增方法时只增加方法文档及主 SKILL 的一条触发入口，不复制主循环，也不强制重新执行其他方法。

## 先复用已有 SKILL 与工具

先查现有 SKILL 是否已有适用内容，通用框架知识优先查已有 Knowledge。
原有 SKILL 暂时保持原样和原语言；等实际测试发现具体问题后再针对修改，不为统一框架而整批重写。
新增流程只按任务范围参考已有内容，不假设原有入口具备统一子任务接口或已验证目标芯片。
计划、预算、记录与验收仍由当前主流程管理；不因加载参考内容扩大任务或另建排名。

把操作映射到当前实际注册的工具：plan_* 管理任务进度，read_file/write_file 保存产物，
shell/shell_jobs 执行与追踪作业，领域工具提取证据，memory_* 保留适合长期复用的结论。
接续上层计划及现有记录，调用前核对 schema、路径可达性、持久化与退出边界；旧文档中的工具名不等于现有实现。
操作细节集中在共享说明中，主流程只标调用位置。调优实例见 [Agent 工具复用](train-ascend-performance-tuning/references/agent-tools.md)。

## 最小验证

先给 Agent 一个具体输入，检查它能否沿正文走完“输入 → 操作 → 结果 → 交付”。
至少检查一次成功路径和一次失败/信息不足路径；能解析 Markdown 不等于 workflow 已打通。
有硬件操作时分别记录离线流程检查、实际执行和效果验证，不能由前者宣称后两者通过。
